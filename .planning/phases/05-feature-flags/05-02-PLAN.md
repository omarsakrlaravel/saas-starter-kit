<task type="auto">
  <name>Task 1: Create FeatureFlagsPage with kill switch section and feature table</name>
  <files>app/Filament/Pages/FeatureFlagsPage.php</files>
  <action>
Create a custom Filament Page at `app/Filament/Pages/FeatureFlagsPage.php`. This is NOT a Resource -- it needs a custom layout with a kill switch section at the top and a table below.

**Page setup:**
- Extends `Filament\Pages\Page`
- Navigation icon: `'phosphor-flag-duotone'`
- Navigation label: 'Feature Flags'
- Navigation group: null (top-level)
- Title: 'Feature Flags'
- Use inline view via `protected static string $view` pointing to a custom view, OR use Filament's built-in page with table integration.

**Approach: Use Filament's `InteractsWithTable` trait** (from `Filament\Tables\Concerns\InteractsWithTable`) and implement `HasTable` interface. This gives us a native Filament table inside a custom page.

**Page structure (two sections in the view):**

1. **Kill Switch Section** (top, rendered via page properties):
   - Query `FeatureDefinition::where('type', FeatureFlagType::KillSwitch)->get()`
   - For each kill switch, show: name, description, and a toggle
   - Toggle state comes from `Feature::for(null)->active($definition->name)`
   - Toggle action calls `Feature::for(null)->activate($name)` or `Feature::for(null)->deactivate($name)`
   - Update `FeatureDefinition` `last_changed_by` and `is_active` on toggle
   - Log to activity log: `ActivityLog::log('feature_flag_toggled', "Kill switch '{$name}' " . ($active ? 'activated' : 'deactivated'))`
   - Style kill switch section with a subtle danger/warning background so admins know it is high-impact
   - Use `requiresConfirmation()` on the toggle action with a danger modal for activating kill switches

2. **Feature Table** (below kill switches):
   - Query: `FeatureDefinition::where('type', '!=', FeatureFlagType::KillSwitch)` (kill switches handled above)
   - Columns:
     - `name` -- TextColumn, searchable
     - `type` -- TextColumn with badge using `FeatureFlagType->color()` and `->label()`
     - `description` -- TextColumn, wrap, limit(80)
     - `is_active` -- ToggleColumn (for global enable/disable)
     - `changedBy.name` -- TextColumn, label "Last Changed By"
     - `updated_at` -- TextColumn, since() format
   - Filters: SelectFilter on `type` using FeatureFlagType enum (exclude KillSwitch since those are shown above)
   - Searchable by name and description

**Table actions (per row):**
   - **Toggle for Organization** action (modal):
     - Opens a modal with a Select field for Organization (searchable, using Organization::query())
     - And a Toggle field for the flag state
     - On submit: calls `Feature::for($organization)->activate($name)` or `Feature::for($organization)->deactivate($name)`
     - Updates `FeatureDefinition->last_changed_by` to current admin
     - Logs: `ActivityLog::log('feature_flag_override', "Feature '{$name}' " . ($active ? 'activated' : 'deactivated') . " for org '{$org->name}'")`

**ToggleColumn behavior for is_active:**
   - When toggling is_active on a non-kill-switch feature, update `FeatureDefinition->is_active` and `last_changed_by`
   - If deactivating (is_active = false), also call `Feature::deactivateForEveryone($name)` to clear all Pennant stored values
   - If activating (is_active = true), call `Feature::purge($name)` to reset all stored values so features re-resolve from their class definition
   - Log the change to ActivityLog

**Create the Blade view** at `resources/views/filament/pages/feature-flags.blade.php`:
- Top section: loop over `$this->killSwitches` with Alpine.js toggle buttons. Each toggle dispatches a Livewire action.
- Bottom section: `{{ $this->table }}` to render the Filament table.
- Keep the view simple -- most logic lives in the PHP page class via Livewire actions and Filament table builder.

**Important:**
- Use `Wave\ActivityLog` for logging (not Laravel Log facade for activity tracking).
- Use `auth()->id()` for `last_changed_by` updates.
- Pennant's `Feature` facade handles the actual flag state in its `features` table. The `feature_definitions` table is metadata only.
- Do NOT build percentage-based rollout UI -- Pennant handles rollout percentages in code.
